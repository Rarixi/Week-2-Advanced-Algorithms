# Chapter 10 Technical Report StringSearchEngine

## Executive summary

This project builds four different ways to search text and wires them all behind one interface so they can actually be compared instead of just described. I implemented Knuth Morris Pratt for deterministic linear time matching, Rabin Karp for randomized fingerprint based matching, a suffix array with Kasai's LCP algorithm for indexed search, and a compressed suffix trie for the same job from a different angle. On top of those four I built three real applications, a plagiarism detector, a DNA gene scanner, and an autocomplete engine, each one picked specifically because it plays to one algorithm's actual strength rather than just using whichever one was handy. I ran all four algorithms against texts up to a million characters and the story that came out matches the theory closely, with one honest exception I spend real time on below, the suffix tree's construction cost turned out to be the single biggest practical limiter in the whole project, bigger than anything the complexity tables usually warn you about.

## Overview of string matching complexity

Every algorithm here answers the same question, where does a pattern of length m occur inside a text of length n, but they pay for the answer in different currencies. KMP computes a failure function over the pattern once, O(m), then scans the text once, O(n), never moving backward, giving O(n plus m) total no matter how adversarial the input is. Rabin Karp instead hashes every window of the text in O(1) per window after an O(m) setup, giving the same O(n plus m) average case, but its worst case degrades to O(n times m) if the hash function collides constantly, which is exactly why verification against the real substring matters, a hash match is a candidate, never a guarantee. The suffix array takes a completely different approach, instead of scanning the text for one pattern, it sorts every suffix of the text once, O(n log n), so that afterward any pattern can be found with a binary search, O(m log n). The suffix tree does the same job as the suffix array but as an explicit tree instead of a sorted list, letting a query like longest repeated substring or distinct substring count fall out of the tree's own shape in O(n) rather than needing a separate pass over an LCP array.

## Implementation details

Correctness mattered more to me in this project than in most, because these four algorithms are different enough that cross checking them against each other is genuinely informative, not just a formality. Every core algorithm gets checked against a brute force reference on random strings, and the suffix array's longest repeated substring (read off the LCP array) gets checked against the suffix tree's own independent answer (read off which node has the most distinct ways to continue past it). That second check actually caught a real bug while I was building it, my first version of the suffix tree's repeat detector only looked for nodes with two or more children, which misses the case where one suffix ends exactly where another one continues, banana's repeated "ana" is the smallest example of this, and the cross check against the suffix array's answer is what surfaced it. One other design choice worth calling out, every edge in the suffix trie stores a pair of indices into the original text rather than a copied substring, because a trie over a text with every character distinct would otherwise need to store on the order of n squared characters just for the edge labels, a classic suffix tree space trap that index based edges sidestep entirely.

## Benchmark analysis

The benchmark sweeps KMP, Rabin Karp, and the suffix array from 10,000 up to 1,000,000 characters, with the suffix tree getting its own smaller sweep up to 100,000 for reasons the trade offs section explains. At the full million character size, KMP finished in about 0.10 seconds and Rabin Karp in about 0.51 seconds, both comfortably linear. The suffix array told a very different story, about 7.32 seconds just to build, against a search time afterward of about 0.00004 seconds, which is the entire point of paying that cost once. The suffix tree at its largest tested size, 100,000 characters, took about 1.44 seconds to build and produced 162,157 nodes, while the suffix array at that same size built in under half a second. The collision analysis is the clearest result in the whole report, at a modulus of 101 Rabin Karp's collision rate was about 95 percent, 195 hash matches needed full verification to find just 10 real occurrences, and by the time the modulus reached 10,007 the collision rate dropped to exactly zero on the same text and pattern, with the real default modulus of 2 to the 61st minus 1 giving the same clean zero.

## Trade offs

Preprocessing versus runtime is the single biggest theme here. KMP and Rabin Karp do essentially no preprocessing, their setup cost scales with the pattern, not the text, so every single search redoes a full linear scan. The suffix array and suffix tree flip that completely, a large upfront cost in exchange for near free repeated queries, which only pays off once you're actually running many searches against the same text, exactly what core/search_engine.py's recommend method is built to point out from its own recorded call history rather than just asserting it as a rule of thumb. Deterministic versus randomized is the second theme, KMP's O(n plus m) bound holds no matter what the input looks like, while Rabin Karp's average case bound depends on the hash function behaving well, and the collision benchmark shows exactly how badly that assumption can fail, a weak modulus doesn't just slow things down a little, it pushes the algorithm most of the way back toward the O(n times m) worst case it's supposed to avoid. Memory versus speed is the trade off the benchmark surfaced that I didn't fully expect going in, the suffix array's memory use grew from about 1.3 megabytes at 10,000 characters to about 137 megabytes at 1,000,000, and the suffix tree's growing similarly to about 83 megabytes at just 100,000 characters, against KMP and Rabin Karp's memory staying flat under 2 kilobytes the entire time since their footprint scales with the pattern, not the text. That's a real cost of indexing, not just a footnote.

## Applications

Each application here leans on a different algorithm's actual strength rather than defaulting to whichever one feels familiar. The plagiarism detector uses Rabin Karp to batch check thousands of overlapping phrases from one document against another in a single pass, which is precisely the batch matching scenario Rabin Karp is built for, and uses a generalized suffix array, both documents concatenated around a sentinel character, to find the single longest substring they share outright, a fact the suffix array's own LCP values prove about themselves with no separate alignment algorithm needed. The DNA gene scanner builds one suffix array or suffix tree per genome and then checks an entire panel of known genes against it, reusing that one index for every gene in the panel instead of rescanning the genome once per gene, the amortization story made concrete. Autocomplete turned out to need a genuinely different structure, a prefix trie over independent vocabulary words with frequency weighting, rather than reusing the suffix tree, because autocomplete asks which separate words share a prefix, not where a substring occurs inside one shared document. These three applications map closely onto where search engines, bioinformatics tools, and compilers actually use string matching in practice, batch phrase matching for ranking and detecting duplicate content, indexed substring search for genome scale data that gets queried over and over, and prefix structures everywhere from autocomplete to a compiler's own symbol tables.

## Conclusion

The engineering lesson that stuck with me most from this project is that construction cost deserves just as much attention as query cost, not less. A structure that answers queries in microseconds once built is only actually fast if you can afford to build it, and the suffix tree's construction time here, worse than the suffix array's at every size I tested, is exactly why it got its own smaller benchmark sweep instead of silently running it at a scale where the results would stop being a fair comparison. KMP's steady, boring, always linear behavior and Rabin Karp's collision rate falling off a cliff the moment the modulus got reasonable both reinforced the same point from opposite directions, the right algorithm depends entirely on how the text gets used afterward, once versus many times, trusted input versus adversarial, and no single one of these four is simply the best choice in general.
