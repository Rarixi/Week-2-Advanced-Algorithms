# Week 7 Report Randomized Algorithms

## Executive Summary

This week was about randomness doing two totally different jobs depending on the problem. In randomized quicksort and randomized selection, randomness is a defense move, it stops any single input pattern from reliably triggering the worst case, since the bad pivot choice that would cause it only happens by random chance instead of by what the input looks like. In Monte Carlo primality testing, bloom filters, and minhash, randomness flips roles and becomes the thing doing the actual estimating, trading a small, controllable chance of being wrong for huge savings in time or memory. Quicksort showed this split most clearly since I had to build a true fixed pivot version just for this comparison, Week 2's own quicksort already picks a random pivot, so there was no honest deterministic baseline sitting in the repo already. Primality testing showed the probability side best, fermats test got fooled by carmichael numbers almost a third of the time at low k while miller rabin never did, even once. Across all five parts the same idea kept showing up, a little randomness, used carefully, buys either safety from bad luck or a shortcut past work that would otherwise be too slow to do exactly.

## Methodology

I timed everything with perf counter, averaged over five runs, and also tracked the variance across those runs since this week specifically asked about runtime variance, not just the mean, the plots now show that variance directly as error bars on every runtime line instead of leaving it sitting in a CSV column nobody looks at. Everything ran on my own machine, rari, using plain python and matplotlib, nothing cloud based. For quicksort I used random arrays from size 100 up to 100000 as the main comparison, plus a smaller sweep up to 4000 using already sorted input, the pattern that actually triggers the deterministic version's worst case, going further there would take way too long to be practical. For selection I used sizes 100 up to 100000, checking minimum, median, and maximum each time, recording recursion depth plus how often a chosen pivot landed in the middle half of its subarray, the usual definition of a good split. For primality testing I tested a pool of 150 random composite numbers plus a separate pool of known carmichael numbers, since that's exactly where fermats test is known to struggle, each one checked 10 times per k value at k equal to 5, 10, and 20, and I added each test's theoretical error bound right alongside the measured rate this time, one quarter to the k for miller rabin and one half to the k for fermat's looser bound. For the speed comparison I went from just over a million up to about one hundred billion, all confirmed prime by both the deterministic check and miller rabin agreeing. For the bloom filter I sized it for 5000 expected items at a 1 percent target false positive rate, then kept inserting items past that point to sweep load factor from 0.1 up to 3.0, checking the measured false positive rate against 20000 fresh absent lookups each time, and I also tracked a plain python set holding those same items alongside it, as the deterministic counterpart to compare memory against. For minhash I built one pair of token sets with a known true jaccard similarity around 0.42, then measured estimation error at signature sizes from 16 up to 512, averaging 30 trials per size since minhash's error varies trial to trial, and separately timed minhash against computing exact jaccard directly, its deterministic counterpart, across set sizes from 100 up to 30000.

## Results

### Expected vs Actual Comparisons and Runtime Variance

Randomized quicksort's comparison counts tracked the theoretical 2n times natural log of n curve closely. At 100000 elements the formula predicts around 2.3 million comparisons, the measured count came in at about 1.97 million, close enough given the formula is a leading order estimate and smaller terms get dropped. Variance on random input turned out to be the less clean story. I expected one pivot strategy to consistently show more run to run spread than the other, but once I actually plotted the error bars across every size, there wasn't a stable winner, sometimes randomized's spread was bigger, sometimes deterministic's was, and it flipped around between separate runs of the same benchmark on the same sizes. With only five repeats per measurement that's honestly expected, five samples just isn't enough to pin down a reliable variance estimate, and whatever noise rari's own CPU scheduling adds on a given run probably swamps any real difference between the two pivot strategies on non adversarial input. The worst case comparison tells a completely different, far more reliable story though, see below.

The worst case sweep makes the real effect obvious instead. At 4000 elements on already sorted input, randomized quicksort finished in about 5444 microseconds using 51668 comparisons, deterministic quicksort took about 589047 microseconds using 7998000 comparisons, a gap of around 108 times on runtime and 155 times on comparisons. That gap held up cleanly every time I reran it, nothing noisy about it, which is exactly the difference between a worst case that only shows up for one specific pivot strategy and ordinary run to run timing jitter that shows up for both.

### Success Probability and Recursion Depth in Selection

Randomized selection's good split fraction, how often a chosen pivot landed in the middle half of its subarray, stayed in roughly the 35 to 50 percent range the textbook expectation of around 50 percent would predict, across basically every size and every choice of k. At 100000 elements the median query gave a good split fraction of about 43 percent and a recursion depth of 21, not too far off minimum's depth of 20, with maximum resolving fastest at a depth of 13. Recursion depth bounced around more between separate runs than I expected going in, since which pivots happen to land well is itself random, but it never came close to scaling with n itself, staying in the tens even at 100000 elements, which is the real point, randomized selection's expected linear time guarantee comes from recursion depth staying logarithmic almost always, not from it being some fixed small number every single run. The genuinely surprising result was that plain sort then index actually beat randomized selection outright at finding the median, 24195 microseconds versus 33474 at 100000 elements. Randomized selection's expected linear time advantage never showed up in practice, since python's built in sort runs in fast C code while my quickselect recursion is pure python, and that constant factor gap swamped the asymptotic one at every size tested. For minimum and maximum though, randomized selection won clearly, needing far fewer recursive calls, 19881 microseconds versus 28826 for minimum and 15451 versus 25217 for maximum.

### Error Probabilities Across k and Speed vs Deterministic

Across 150 random composite numbers, neither fermats test nor miller rabin got fooled even once at k equal to 5, 10, or 20. That isn't both tests being equally strong, it just shows most composite numbers are easy to catch, plenty of random witnesses expose them. The real difference only showed up against carmichael numbers, composites built specifically to resist fermats test. At k equal to 5, fermats test got fooled 28 percent of the time there, dropping to 12 percent at k equal to 10, only reaching zero at k equal to 20. Miller rabin, on the exact same carmichael numbers, was never fooled at any k. Plotting each test's own theoretical error bound alongside that measured rate makes the asymmetry even sharper than the raw percentages suggest. Miller rabin's bound at k equal to 5 is one quarter to the fifth power, about 0.098 percent, and its measured carmichael rate of 0 percent sits comfortably under that the whole time. Fermat's loose bound at the same k is one half to the fifth power, about 3.125 percent, and its measured carmichael rate of 28 percent blows straight through that bound by about 9 times. That's not a small miss, fermat's own advertised worst case guarantee simply does not hold against carmichael numbers, which is exactly the known weakness these numbers were built to expose, miller rabin's bound holds everywhere I measured it. For the speed comparison, deterministic trial division took about 11297 microseconds at just over one hundred billion, while fermat and miller rabin took about 166 and 137 microseconds respectively at that same size, both roughly 70 to 83 times faster than trial division, a gap that only grows with n.

### False Positive Rate vs Load Factor and the Memory Accuracy Trade Off

My bloom filter was sized for 5000 expected items at a 1 percent target false positive rate, working out to a bit array of 47926 bits using 7 hash functions. At a load factor of 0.1, items inserted divided by bit array size, the measured false positive rate was 0.83 percent, just under the 1 percent target and matching the theoretical prediction of about 0.82 percent almost exactly. Pushing the load factor up to 1.0, nearly ten times more items than the filter was sized for, drove the measured rate up to 99.3 percent, basically every bit ends up set once it's overloaded that badly. That's the whole trade off in one picture, a bigger bit array for the same item count buys a lower false positive rate directly, you're paying memory for accuracy on a sliding scale with no trick around it. Tracking a plain python set holding those same items side by side with the bloom filter made the memory half of that trade off concrete instead of theoretical. The bloom filter's bit array stayed at a flat 5991 bytes the entire time, since its size is fixed the moment you pick expected items and target false positive rate, no matter how many items actually get inserted afterward. The equivalent set, by contrast, grew the whole time, starting around 422551 bytes at 4793 items and reaching 13141424 bytes by 143778 items, about 2194 times bigger than the bloom filter at that same point. That's the actual price of exactness, a set that can tell you definitively whether an item was ever added costs memory that scales with how many items you put in it, while the bloom filter trades away that certainty, accepting a small, tunable false positive rate, for memory that doesn't grow at all.

### True vs Estimated Jaccard Similarity

My two test sets had a true jaccard similarity of about 0.418. At a signature size of only 16 hash functions, minhash's mean estimate came out to 0.435, a mean absolute error of about 0.084 averaged over 30 trials. Pushing the signature size to 512 brought the mean estimate to 0.419, basically dead on, with mean absolute error dropping to about 0.019. Going from 16 to 512 hash functions, a 32 times increase, cut average error by about 4.4 times, roughly in the ballpark of what 1 over square root of k would predict, square root of 32 is about 5.7, so a bit better than that simplest version suggests but close enough that the underlying idea clearly holds. Timing minhash against computing exact jaccard directly on the same pairs of sets told a much less flattering story for minhash though, if speed on a single comparison is all you care about. At a set size of 100, exact jaccard took about 12 microseconds while minhash took about 6562, nearly 546 times slower. The gap stayed huge across every size I tested, still around 264 times slower even at 30000 elements per set. Minhash is doing strictly more work for a one off comparison, it has to hash every element through k separate hash functions just to build the signature, while exact jaccard only has to intersect and union the sets once. The real payoff was never meant to show up here, minhash's whole point is that the signature itself is small and fixed size no matter how big the original sets are, so you build it once, store it, and reuse it for cheap approximate comparisons against many other signatures later, without ever touching the original sets again. For a single throwaway comparison between two sets you already have in hand, exact jaccard wins outright, and my numbers make that completely unambiguous.

## Discussion

### When Randomization Helps vs When It Does Not Change Much

Randomization earns its keep most clearly when input could be adversarial or simply unknown ahead of time, exactly quicksort's situation, you can't control what data someone hands you. It also clearly wins inside Monte Carlo testing against known hard cases like carmichael numbers, where fixed witnesses would be a real liability. Where it helped less this week was selection by median, since python's constant factor overhead on pure python recursion beat out the supposed linear time advantage completely, a good reminder that big O describes what happens as input size goes to infinity, not necessarily what happens on the machine in front of you today.

### Trade Offs Between Speed Accuracy and Memory

Bloom filters made this trade off the most visible, since load factor versus false positive rate is basically a dial you can turn directly, smaller filter means less memory and a higher error rate, bigger filter means the reverse, and nothing about the hash functions themselves changes that relationship. Comparing the bloom filter against a plain set holding the same items put a real number on what that trade actually buys you, a flat 5991 bytes no matter how many items came in, against a set that grew to over 13 million bytes, a difference the size of the trade off, not just the direction of it. Minhash showed a softer version of the same thing, more hash functions means a bigger signature to store and more work per comparison, in exchange for a tighter similarity estimate, and diminishing returns were visible in my own numbers, doubling k from 256 to 512 barely moved the error compared to the much bigger jump from 16 to 32. Minhash's own timing against exact jaccard made clear this trade off is about storage and reuse, not raw speed, since for a single comparison exact jaccard beat minhash by a few hundred times every size I tried.

### Real World Applications

Randomized quicksort and selection show up anywhere a general purpose sorting or ranking library needs to handle unknown, possibly adversarial input without anyone having to think about it, which is why most real world sorting libraries use some form of randomized or hybrid pivoting under the hood. Monte Carlo primality testing is the backbone of how real cryptographic systems generate large primes quickly, since trial division on numbers hundreds of digits long would never finish in a human lifetime. Bloom filters show up constantly in systems that need a fast, cheap first check before doing something expensive, browsers use them to check if a url might be malicious before a real lookup, databases use them to skip disk reads for keys that definitely aren't present. Minhash powers near duplicate detection across huge document collections and plagiarism checking, where comparing every pair of documents directly would be completely impractical at scale.

## Conclusion

Coming into this week I mostly thought of randomness as a trick for dodging bad luck, true for quicksort and selection, but the Monte Carlo side reframed it as closer to a tool for buying speed or memory back by accepting a controllable, shrinkable amount of risk. The carmichael number result was the clearest proof of that, fermats test genuinely has a real weakness, not just a theoretical one, and miller rabin's extra structure genuinely closes it, not just on paper but in numbers I measured myself. The selection result where sorting beat quickselect outright was a good reminder too, that theory tells you how something scales, not necessarily which one wins on the machine and sizes you actually care about right now. Both lessons feel like they'll matter well past this one assignment.
