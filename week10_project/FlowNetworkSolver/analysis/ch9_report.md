# Week 10 Technical Report FlowNetworkSolver

## Executive summary

This project builds a flow network solver from scratch and uses it to power three real applications. I implemented three max flow algorithms, Edmonds Karp, Push Relabel, and Min Cost Max Flow, then built bipartite matching, image segmentation, and scheduling on top of them as straight reductions to flow problems. I tested every algorithm against an independent brute force or DFS reference solver so I wasn't just trusting my own code to check itself, and I ran a full benchmark suite that pushed networks up to 14,400 nodes and 57,120 edges. The biggest story in this report isn't really "which algorithm wins." It's that Push Relabel looked completely broken until I added the gap heuristic, and once I did it went from unusable to genuinely competitive. That one fix is probably the single most useful thing I learned this week, so I spend a good chunk of this report on it.

## Theory overview

A flow network is a directed graph where every edge has a capacity, and a flow assigns each edge a value that never exceeds that capacity while keeping every node other than the source and sink balanced, meaning flow in equals flow out. The max flow problem asks for the largest amount of flow you can push from a source to a sink under those constraints. The key tool for both finding and proving optimality of a max flow is the residual graph, which tracks, for every edge, how much additional flow could still be pushed forward and how much could be undone by pushing backward. As long as the residual graph still has a path from source to sink, the current flow isn't maximum yet, because you could push more along that path. That's the max flow min cut theorem in a nutshell. When no path remains, the set of nodes still reachable from the source forms one side of a minimum cut, and the value of the max flow equals the total capacity of the edges crossing that cut. This is exactly what lets a flow algorithm double as a way to find an optimal partition of a graph, which is what makes the image segmentation application work later on.

Min cost flow adds a second dimension on top of this. Instead of just asking how much flow you can push, it asks how much flow you can push for the least total cost, where every edge now carries both a capacity and a per unit cost. The optimality condition here isn't just "no augmenting path exists," it's "no negative cost cycle exists in the residual graph," which is why the algorithm has to track potentials and reduced costs rather than just searching blindly.

## Algorithm comparison

Edmonds Karp is the simplest of the three. It repeatedly finds the shortest augmenting path using breadth first search and pushes flow along it, and that single choice, always taking the shortest path rather than just any path, is what caps it at O(V times E) iterations no matter how large the capacities get. It's easy to reason about and easy to get right, and in my benchmark it was consistently the fastest solver on sparse and medium sized graphs. At 14,400 nodes and 57,120 edges it finished in about 2.13 seconds using only 26 iterations.

Push Relabel is supposed to be the asymptotically faster option, O(V squared times E) against Edmonds Karp's looser bound, because it abandons the always valid flow discipline and works with a preflow instead, letting excess pile up at nodes and get pushed downhill using height labels. In practice this is where I learned the most. My first working version used plain FIFO discharge with only a current arc optimization, and it was catastrophic on anything resembling a real graph. A 45 by 45 grid, just 2,025 nodes, took over a minute and around 7 million push and relabel operations before I added the fix. The problem is that once part of the graph gets disconnected from the sink, nothing stops a node there from getting relabeled one height at a time forever, chasing a sink it can never reach. The fix is the gap heuristic. I keep a count of how many nodes sit at each height, and whenever a relabel empties out a height band completely, every node sitting strictly above that band gets bulk relabeled in one pass straight up to a height that marks it as disconnected, instead of discovering that fact one relabel at a time. After that single change, the same grid dropped to about 1.23 seconds in the final benchmark run, and the algorithm scaled all the way to 14,400 nodes in under 25 seconds, with 14,397 of its relabels being bulk gap relabels doing work that would otherwise have taken ages one node at a time.

Min Cost Max Flow trades raw speed for the ability to optimize an objective, not just a quantity. It runs successive shortest paths using Bellman Ford once up front and Dijkstra with reduced costs after that, maintaining node potentials so the reduced costs never go negative. On the three way comparison it was reliably the slowest of the three, 1.34 seconds at 1,500 nodes against Edmonds Karp's 0.18 seconds and Push Relabel's 0.30 seconds, which makes sense since it's doing strictly more work per round to track cost optimality on top of just finding flow.

## Applications

Bipartite matching reduces to max flow by connecting a source to every node on the left with capacity one, a sink from every node on the right with capacity one, and an edge of capacity one between every allowed pair. The resulting max flow value is exactly the size of the largest matching, and I validated this against a brute force matcher on small random instances.

Image segmentation uses the Boykov Jolly construction, where every pixel is a node with a link to a foreground terminal weighted by how well it matches a foreground model and a link to a background terminal weighted the same way for the background, plus neighbor links weighted by how similar two adjacent pixels look. The minimum cut this produces splits the image into foreground and background in a way that respects both the per pixel evidence and the neighbor smoothness, and I tested it on a synthetic image with a clean light and dark boundary to confirm the separation lands exactly where it should.

Scheduling reduces to max flow the same general way, a source feeding each job at its demand, jobs connecting to the machines they're allowed to run on, and machines draining into a sink at their capacity, so the max flow tells you the largest feasible assignment and whether every job's demand was fully met.

## Performance findings

Across every single comparison in the benchmark, every algorithm agreed on the max flow value or the min cost, which matters more to me than any of the timing numbers since it means the implementations are actually correct and not just fast. The timing story is nuanced though. Edmonds Karp won almost everywhere, but on the dense 150 node case, 3,507 edges packed onto 150 nodes, Push Relabel actually beat it, 0.064 seconds against 0.107 seconds, because dense short range connectivity plays to Push Relabel's strengths while Edmonds Karp still has to do a fresh breadth first search every round. Memory told a similar story in reverse. Edmonds Karp stayed lean, about 1.3 megabytes at 14,400 nodes, while Push Relabel grew to around 12.5 megabytes at the same size, the price of tracking height, excess, and current arc state for every node plus the gap bookkeeping.

## Conclusion

The real engineering lesson here is that an asymptotically better algorithm isn't automatically a practically better one, and the gap between those two things can be enormous, 67.8 seconds down to a fraction of a second enormous, if you're missing one heuristic that the theory assumes you'll add. Edmonds Karp earns its reputation as the dependable default for exactly this reason, its simplicity leaves nowhere for that kind of gap to hide. Push Relabel can clearly scale, reaching tens of thousands of nodes once properly implemented, but it only gets there with real engineering care layered on top of the base algorithm. That's the piece I'll carry forward past this assignment.
